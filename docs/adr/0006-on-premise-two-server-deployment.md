# ADR-0006: Deploy แบบ on-premise 2 เครื่อง (App Server + Data Server) แทน cloud

- **สถานะ:** Accepted — **บันทึกย้อนหลัง: ตัดสินใจไปแล้วก่อนใช้ Buaflow**
- **วันที่ตัดสินใจจริง:** ไม่ทราบวันที่แน่ชัด (ก่อนเริ่มใช้ Buaflow) · บันทึกย้อนหลังวันที่ 2026-09-24
- **ผู้ตัดสินใจ:** ทีมพัฒนา EV Rental GO

## บริบท
ระบบต้อง deploy รองรับฟลีตสูงสุด ~100 คัน พร้อมข้อมูลลูกค้า (e-KYC เอกสารบัตรประชาชน, ใบขับขี่) และข้อมูลการเงิน
(billing, payment) ซึ่งเป็นข้อมูลอ่อนไหวภายใต้กฎหมายไทย

## ทางเลือกที่พิจารณา

### ทางเลือก 1: Cloud (เช่น AWS/GCP/Azure managed services)
- ข้อดี: scale ง่าย, มี managed service (RDS, ElastiCache ฯลฯ) ลดงาน ops
- ข้อเสีย: ค่าใช้จ่ายรายเดือนต่อเนื่อง, ข้อมูลอ่อนไหว (บัตรประชาชน, การเงิน) ต้องผ่าน third-party cloud provider

### ทางเลือก 2: On-premise 2 เครื่อง (App Server + Data Server)
- ข้อดี: คุมที่ตั้งข้อมูลได้เอง (รองรับข้อกังวลด้าน PDPA), ต้นทุนคงที่ไม่ผันแปรตาม usage, latency ต่ำสำหรับ MQTT broker ที่ต้องรับ connection จากรถในประเทศไทย
- ข้อเสีย: ทีมต้องดูแล infra เอง (patch, backup, HA) ไม่มี managed service ช่วย, scale ต้องซื้อเครื่องเพิ่มเอง

## การตัดสินใจ
**เลือก: On-premise 2 เครื่อง — Server 1 (App Server: Next.js + IoT Gateway + Mosquitto), Server 2 (Data Server: PostgreSQL/TimescaleDB + Redis) รองรับเป้าหมายสูงสุด ~100 คัน**

เหตุผล:
- ควบคุมข้อมูลลูกค้า/การเงินให้อยู่ภายใต้การดูแลของทีมเองโดยตรง (ข้อกังวลด้าน PDPA) และคุมต้นทุนให้คงที่แทนที่จะจ่ายตาม usage แบบ cloud

## ผลที่ตามมา
**ผลดี:**
- ต้นทุนคาดการณ์ได้ ไม่ผันแปรตามปริมาณ GPS telemetry ที่เข้ามาต่อเนื่องทุกวัน
- ข้อมูลอ่อนไหว (บัตรประชาชน, ใบขับขี่, ข้อมูลการเงิน) ไม่ต้องออกจาก infra ที่ทีมควบคุมเอง

**ผลเสีย / สิ่งที่ต้องยอมรับ:**
- ไม่มี auto-scaling / managed backup ของ cloud — ทีมต้องทำ backup/monitoring/patch เอง
- Single point of failure ต่อเครื่อง (ไม่มี multi-AZ) — ถ้า Data Server ล่ม ระบบทั้งหมดหยุดจนกว่าจะกู้คืน
- ยังไม่มีหลักฐาน rollback/disaster-recovery rehearsal ที่บันทึกไว้ (พบใน `buaflow assess` ว่า R3 control ด้าน rollback/observability ยังไม่ผ่าน)

**สิ่งที่ต้องทำเพิ่มเพราะเลือกแบบนี้:**
- ต้องมีแผน backup/DR ที่ทดสอบจริงก่อนอ้าง readiness ระดับ R3 (ติดตามใน `docs/evidence/readiness.json`)

## ทบทวนเมื่อไหร่
ถ้าฟลีตโตเกิน ~100 คันจนสองเครื่องไม่พอ หรือถ้าทีมต้องการ HA/DR ที่คุ้มค่ากว่าการซื้อเครื่องสำรองเอง
